语义 BOM 抽取评测平台

把「合同条款抽取规则」从手工艺变成可编译、可审计、可自动调优的工程化能力 —— 多模态数据湖里的「规则实验室 + 评测引擎」。

当前阶段：核心功能已建成（生成全链路跑通 + 真实数据验证）· 优化闭环设计中 · 独立模块，不替代抽取平台
这是什么

一句话：抽取规则的「编译器」

就像代码编译器把源码变成可执行程序——

  • 输入：一份测试集（标注了"这条合同里有哪些条款、期望抽出来什么"）。
  • 自动产出：一套结构化的语义 BOM（条款的"规则蓝图"）+ 一段可直接粘贴到抽取平台的提示词。
  • 效果：业务不再手搓长 prompt，上传测试集 → 一键生成 → 复制粘贴跑分。规则像代码一样可版本、可对比、可回滚。
给谁用：业务/规则工程师（自助生成+调优规则）、数据湖抽取链路（提供可审计的规则产物 + 评测闭环）。不直连平台、不替代质量运营。
01 · 解决什么问题

合同抽取调优，业务三难

难点 1

规则靠手写，质量不稳

抽取规则散在 prompt 文本里，凭经验写，无结构、无版本。新条款上线 = 重新手搓，准确率难保证（起步仅 52%）。
难点 2

迭代靠手工，不可复现

发现错例 → 人工改 prompt → 粘平台跑分。改了啥、为啥改、有没有改坏，全凭记忆，无法追溯。
难点 3

错例根因靠猜

漏抽/误抽了，到底是"关键词没覆盖"还是"规则没识别"？没有分层，定位全靠猜，改不到位。
本质：调一个条款，要在平台、大模型、Excel 间反复粘贴、手改提示词、凭感觉回归——慢、累、不可复现。

03 · 怎么工作（2/3）

BOM：条款的「规则蓝图」

BOM = 把业务对一个条款的理解，拆成机器能照着抽取的结构化规则。不再是一坨 prompt 文本。

📦 语义 BOM（版本化 · 可审计 · 可对比）
  • 语义定义 — 这个条款是啥（自然语言 + 排除说明）
  • 绝对拦截规则 — 命中就放弃（防误抽，分场景）
  • 核心匹配规则 — 满足就提取（防漏抽，分场景）
  • 毒药词 — 一票否决，命中即非本条款
  • 排雷思维链 — 抽取前必走的排雷步骤，引导大模型推理
  • 召回画像 — 关键词/易混淆词/章节/语义查询（召回锚点）
  • 典型正例 + 分析理由 — 进提示词帮大模型理解，理由锚定规则 新
类比：BOM 就像菜谱——定义是"这道菜是啥"，拦截是"这些情况不算这道菜"，匹配是"满足这些才是"，毒药词是"放了这个料就绝对不是"。
03 · 怎么工作（3/3）

典型正例 + 分析理由：教大模型"抽啥"

对齐新平台抽取逻辑：提示词里放几个典型正例，每个带"为什么这是正例"的分析理由，帮大模型理解要抽的语义边界。

  • 理由锚定 BOM 规则：每个理由必须引用具体匹配规则解释命中（"依据匹配规则X，本例含…故命中"）+ 确认不触发拦截。
  • 程序化一致性校验：自动检查每个正例——被拦截规则命中？匹配规则没覆盖？不一致就红旗告警（说明 BOM 有问题，回头改 BOM，不是让理由将就）。
  • 用户可编辑：界面上改正例值/理由，提示词实时重组装。业务能微调，不依赖技术。
解决的问题：以前理由和规则可能矛盾（理由说 A、规则说非 A），现在强制一致 + 自动校验兜底。

05 · 优化闭环（设计中）

把"专家手工调"工程化

生成的 BOM 跑出 badcase 后，半自动闭环优化——人审断点保障不回归。

① 导入 badcase→ ② 自动判类→ ③ 针对性优化→ ④ 红/绿 diff 对比→ ⑤ 人审应用
  • 自动判类：badcase 分两类——召回失败（关键词没覆盖，改画像）vs 抽取失败（召回到了没识别，改规则）。用户手填为主，空的系统启发式判（标"待复核"）。
  • diff 对比：新版本 vs 旧版本，红删绿增（像代码 diff），改了啥一目了然。
  • 人审应用：确认才生效，防回归；每次优化有审计记录。

07 · 价值

降门槛、可解释、可优化、解耦

减少 Prompt 工程

业务自助生成/优化规则，不再依赖手写长 Prompt、不再依赖技术同学。

可解释可追溯

持续优化引擎

解耦不侵入

不改造抽取平台，导入导出桥接；不与质量运营重复。独立模块，接入数据湖。
